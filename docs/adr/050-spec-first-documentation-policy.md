# 050: ドキュメント運用方針 — spec-firstへの転換

- **status**: accepted
- **date**: 2026-04-29

> このADRは起票時点での決定を記録したスナップショットである。
> 現在の仕様は spec / doc-policy.md を参照すること。

## 背景

brewprintのドキュメントはこれまでADR中心で運用してきた。
`doc-policy.md` §3には「ADRが中心である理由」として、設計判断の積み重ねを残すことが重要であると明記されており、新しい設計判断はまずADRに記述され、specはADRから派生するreferenceという位置づけだった。

しかしimpl ↔ ADR/spec整合性レビューを進める中で、構造的な問題が表面化した。

### 問題1: ADRが「履歴」と「現行仕様」を兼ねている

ADRは設計判断の根拠を残すドキュメントだが、現状は「決定」セクションに現行仕様の記述（表・スキーマ・命名規則など）が大量に含まれている。
このため、新しいADRが立つたびに過去ADRの記述を更新したり、`partial supersede` を付けたりする作業が必要になっている。

具体例（source層レビューで発覚）:

- ADR-030は「`as:` 値一覧表」を持っているが、ADR-039で `er_diagram` が追加されたタイミングで表が更新されていなかった
- ADR-002は `master.yaml` をプロジェクトルートに置く決定をしているが、ADR-043で実質的にsupersedeされており、現行実装に `master.yaml` は存在しない

### 問題2: 「現行仕様の唯一の正」が定まっていない

実装は何を見て書けばよいのか。LLMは何を読めば現状を把握できるのか。
ADRが履歴も含むため、「現行仕様」だけを抜き出すには複数のADRをsupersede関係込みで読み解く必要がある。これは整合性確認のコストを大幅に増やしている。

### 問題3: doc-policy.md §1との内的矛盾

`doc-policy.md` §1には「人間向け → Mermaid図 / LLM向け → signature / dep tree / inspect」とあり、specがLLM向けreference layerとして扱われる構造を示している。
しかし§3では「ADRが中心」と明記され、specが派生物として扱われている。両者は実質的に矛盾しており、運用上の混乱を招いている。

## 決定

### 1. spec-firstに転換する

brewprintのドキュメント運用は今後、**spec-first** に転換する。

- **specは「現行仕様」の唯一の正**である。実装・LLM・読者はspecだけを読めば現状を把握できる。
- **ADRは「設計判断の根拠記録」**である。なぜその仕様になったか、何を却下したか、トレードオフは何だったかを記録する。
- ADRには起票時点での仕様案・規定を記述してよい。ただし**ADR本文の仕様記述は起票時点のスナップショット**であり、後続ADRやspec更新で覆されうる前提で書かれる。「現在の仕様」を確認したい場合はspecを参照する。

### 2. ADRとspecの責務境界

ADRとspecは**時間軸の違い**で役割を分担する。

| ドキュメント | 何を書くか | 役割 |
|---|---|---|
| spec | **現在の仕様**。スキーマ、ルール、フィールド定義、構造、振る舞い | 現行の唯一の正 |
| ADR | **起票時点の決定**: 背景、選択肢、却下理由、トレードオフ、起票時点での仕様案・規定 | 過去の判断の凍結された記録 |

現状を知りたいときは**specを参照**する。なぜそうなったかを辿りたいときは**ADRを参照**する。

ADRの仕様記述は**遡及修正しない**。後続ADR・spec更新で覆された場合も、旧ADRには起票時点の記述を残す（履歴として）。supersededラベルや`migrated_to_spec`メタ情報で関係性を示す。

#### ADRに書いてよい仕様記述の例

- 起票時点での決定の核（例: 「`as:` キーでファイルを分類する」「QualifiedIDは `module/.../id` 形式とする」）
- 決定の意味を伝えるための具体例（例: 「`as: dag` の場合は dag rendererに渡される」）
- 却下案を説明するための仕様候補比較（案A vs 案B の対比表）
- ADRのスコープ内で完結する詳細仕様（後続ADRで分割されるまでは、唯一の記述箇所になる）

これらは「起票時点の記録」として残ってよい。
ただし「現在も有効か」を判断する場合はspecを参照すること。

#### ADRに書くべきでない記述

- 過去のADRの内容を遡及修正する記述（履歴改竄になる。新ADRで上書きする形にする）
- 「全ての仕様はspecに書く」と機械的に削ぎ落とした、判断の中身が伝わらない記述

#### 起票時点スナップショットの明示

新規ADRには冒頭に以下の一文を入れる。doc-policy.md §3に記述があるため必須ではないが、ADR単体で読まれた場合の見落としを防ぐために推奨する。

```markdown
> このADRは起票時点での決定を記録したスナップショットである。
> 現在の仕様は spec を参照すること。
```

### 3. 双方向リンク

ADRとspecは双方向にリンクする。

- ADR → spec: 「決定」セクションに `> 仕様詳細: [docs/spec/xxx.md](../spec/xxx.md) §N` を明記
- spec → ADR:
  - Front Matter の `depends_on` に関連ADRを列挙（既存ルールを踏襲）
  - 本文中、特定の決定に基づくセクションには `> 由来: ADR-NNN §M` を末尾に注記

これにより、仕様を知りたい人はspecだけを読め、決定の経緯を辿りたい人はADRに飛べる。

### 4. 既存49 ADRの扱い: 漸進移行

既存ADR（ADR-001〜049）は一括書き換えしない。
今後の整合性レビューや新ADR起票で「触れたタイミング」で、該当ADRの「決定」セクションに含まれる現行仕様記述をspecに移管する。

移行作業の手順:

1. 該当ADRの「決定」セクションから、現行仕様にあたる記述（表・スキーマ・ルール本体）を抽出
2. 対応するspecに反映（または新規specを作成）
3. ADRの「決定」セクションを「何を決めたか」の概要 + spec参照リンクに書き換える
4. ADR冒頭に `> このADRの仕様詳細は [docs/spec/xxx.md](../spec/xxx.md) を参照` を追加
5. spec側に `> 由来: ADR-NNN §M` を該当箇所に追記
6. ADRに `migrated_to_spec: YYYY-MM-DD` というメタ行を追加（履歴として）

未移行のADRは、その「決定」セクションが現行仕様を兼ねている状態のまま残る。これは過渡期の措置として許容する。

### 6. spec内メタ情報の書き方

各specには以下の形式でADRリンクを残す。

#### Front Matter（既存ルール）

```markdown
---
scope: docs/spec/file-types.md
status: confirmed
last_updated: 2026-04-29
summary: >
  brewprint YAMLのファイル種別分類ルールを定義する。
depends_on:
  - docs/adr/030-yaml-file-type-declaration.md
  - docs/adr/039-er-diagram-composed-view.md
---
```

#### セクション末尾の由来注記

特定の決定に基づくセクションには、本文中に注記を入れる。

```markdown
## ファイル分類ルール

brewprint YAMLは以下の3種別に分類される...

- ノード定義ファイル: `nodes:` キーをトップレベルに持つ
- View定義ファイル: `as:` キーをトップレベルに持つ
- render_index.yaml: ファイル名で識別する

> 由来: ADR-030 §決定, ADR-043 §2
```

Front Matterはspec全体の出自、セクション注記は局所的な決定の出自を示す。

### 8. ADR-050の位置づけ

本ADRは技術設計ADRと同じ番号体系で50番を割り当てる。
brewprintの設計判断ADRとは性質が異なる「メタADR」だが、別系統に分けると探しにくくなるため番号体系は統一する。
今後同様のメタADRが発生する可能性はあるが、その都度通常の連番で起票する。

## 理由

### spec-firstを採用する理由

- 実装は「現行仕様の唯一の正」を必要とする。ADRが履歴と現行仕様を兼ねていると、実装側が複数ADRをsupersede関係込みで読み解く必要がある
- LLMが現行仕様を把握するreferenceは1箇所にあるべき。spec-firstでこの問題を解決できる
- ADRを「履歴」に純化することで、過去ADRを修正する必要がなくなり、ADR管理コストが下がる
- doc-policy.md §1の「specがLLM向けreference layer」という記述と整合する

### 漸進移行を採用する理由

- 49 ADR全部を一括でリファクタするコストは大きく、今すぐの作業として現実的でない
- 新ADRからspec-firstを適用するだけだと、既存ADRと新規ADRで運用が分かれて混乱する
- レビューで触れたタイミングで移行する形なら、移行コストを実作業のついでに分散できる
- 過渡期はADR本体に現行仕様記述が残ることを許容する

### 双方向リンクを採用する理由

- 仕様を知りたい人がspecから根拠ADRに飛べる
- 根拠を知りたい人がADRから現行仕様の詳細にアクセスできる
- 一方向だけだと、ADRから仕様を読み解こうとした人がspecに気づけない / specから根拠を辿りたい人がADRを発掘できない

### ADRに仕様記述を書くことを許容する理由

「ADRに仕様を書かない」と機械的に縛ると、却下案の比較や決定の核が伝わらない記述になる。
実際のADR運用では、ADR-Aで枠を決めて、後続ADR-B/Cで修正というパターンは普通にあり、各ADRの起票時点では仕様を書くのが自然。

- 却下案の比較には「案Aではこう、案Bではこう」という具体仕様候補が必要
- 決定の核（「`as:` キーで分類する」のような）が書かれないと、ADRが「何を決めたか分からないが決まった記録」になる
- ADR-Aで決めた仕様案がADR-Bで覆っても、ADR-Aは起票時点の記録としてそのまま残る方が履歴として有用

ADR本文の仕様記述は「起票時点のスナップショット」であり、現在も有効かはspecで判断する、という運用で両立できる。

### ADR記述を遡及修正しない理由

- 過去ADRを書き換えると、なぜその決定だったかの当時の文脈が失われる
- supersededラベルや`migrated_to_spec`メタで関係性を示す方が、履歴として正直で追跡可能
- 旧ADRと新ADRを並べて読めば、判断がどう変わったか辿れる

### 却下した代替案

- **(a) 既存ADR凍結 + 新ADRからspec-first**: 既存ADRの「決定」セクションが現行仕様を兼ねたまま残り、混乱が継続する
- **(c) 全49 ADR一括リファクタ**: 作業コストが大きすぎて現実的でない
- **メタADRを別系統(META-001等)にする**: 探しにくくなる
- **由来注記をファイル末尾だけにする**: どのセクションがどのADR由来か追跡しにくい
- **由来注記をFront Matterだけにする**: ファイル全体の粒度しか出せず、セクション単位の追跡ができない
- **specをやめてADRだけにする**: 現状の問題が解消しない
- **ADRに仕様記述を一切書かない（厳格分離）**: 却下案の比較や決定の核が伝えられず、ADRの記録としての価値が下がる。「起票時点のスナップショット」と位置づければ柔軟に書けるため、こちらを採用

## 影響

### ドキュメント運用への影響

- `doc-policy.md` を大規模書き換え（本ADRと同時に実施）
- 既存ADRは漸進移行ルールに従って順次更新
- 新規ADRは本ADRの責務境界に従って書く

### 整合性レビューへの影響

- 進行中の `docs/impl/review/handoff.md` 計画を更新する必要がある
- レビューの基準は「ADRと実装」から「specと実装 + ADRに書かれているがspecに書かれていない決定の発掘」の2軸になる
- 各層レビューでspec移行作業が発生する可能性がある（findings に [spec-migrate] ラベルを追加する想定）

### specの新規追加

- `project-layout.md` / `file-types.md` / `naming.md` を漸進移行のなかで作成する
- 新規spec作成時はFront Matterと由来注記の書式を遵守する

### 既存implへの影響

- 直接の影響なし。spec-firstはドキュメント運用の方針であり、impl側の変更を要求するものではない
- ただし、specに書かれた仕様と implの差分が今後 [code-fix] findings として発生する可能性がある
