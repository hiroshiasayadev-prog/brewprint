# Reference: Work-item authoring

- **id**: `spec:product.concepts.authoring_standards.work_item_authoring`
- **status**: draft
- **date**: 2026-06-23
- **parent**: `spec:product.concepts.authoring_standards`

## What this is

Authoring rules for Work Item artifacts.

This guide defines work-item IDs, paths, file shape, metadata, lifecycle, references, and author-facing inputs.

## Non-goals

- Current DRMCP operating status.
- Concrete DRMCP request, response, or diagnostic schemas.
- Requirement or task authoring rules.
- Cross-artifact ownership beyond work-item-specific writing rules.

## Rules

### ID grammar

| Rule | Level |
|---|---|
| New work-item IDs use `<APP>-WORK-<DOMAIN>-<NNN>`. | MUST |
| `<NNN>` is a three-digit, zero-padded sequence scoped by app namespace, artifact kind, and domain namespace. | MUST |
| Authors may use `<APP>-WORK-<DOMAIN>-new` when requesting automatic sequence allocation. | MAY |
| Existing work-item IDs remain unchanged unless a separate migration decision requires changes. | MUST |

The canonical grammar source is `spec:product.concepts.namespace_model.v2_grammar`.

### File path layout

| Rule | Level |
|---|---|
| New work items use `<app>/records/work-items/<domain>/<APP>-WORK-<DOMAIN>-<NNN>-<slug>.md`. | MUST |
| The file name prefix matches the public ID through the sequence segment. | MUST |
| Physical paths are repository locations, not canonical references. | MUST |

The discovery pattern is defined by `spec:product.concepts.repository_layout.record_discovery_paths`.

### File shape

| Rule | Level |
|---|---|
| Use exactly one ATX H1 outside fenced code blocks. | MUST |
| Use `# <PUBLIC-ID>: <Title>` for H1. | MUST |
| Place the bullet metadata block immediately after H1. | MUST |
| Start body content at the first H2 after metadata. | MUST |

Body section schema:

| section | heading presence | substantive content | content |
|---|---|---|---|
| `## Goal` | always | required when `done` | The resolution goal for the source requirement. |
| `## Boundary` | always | required when `done` | What this work item owns and does not own. |
| `## Impact Scope` | always | no requirement | Specs and artifacts affected, with impact descriptions. |
| `## Task flow` | always | no requirement | Order, branching, and dependencies among the tasks in this work item. |
| `## Task Candidates` | always | no requirement | Candidate tasks with scope descriptions. |
| `## Completion Condition` | always | no requirement | Observable conditions that define when the work item is done. |
| `## Evidence` | always | required when `done` | Supporting records, observations, and implementation evidence. |

All canonical work-item headings use English.

All canonical sections must be present when creating the record, to preserve a stable document shape. Sections not yet written may contain `TBD`.

### Metadata schema

Work-item metadata uses H1-adjacent bullet fields.

| field | create input | partial update | persisted work item | meaning |
|---|---|---|---|---|
| `id` | generated | not updated | required | The public work-item ID. Generated by MCP from the top-level exact ID or server-resolved `new` ID. Must match H1. Do not supply as a metadata field in a create request. |
| `status` | required | optional | required | Current work-item lifecycle state. |
| `date` | required | optional | required | Date the work item was opened or last received a substantive scope change. |
| `source_requirement` | required | optional; correction only | required | The requirement ID this work item addresses. |
| `impact_refs` | required; empty allowed | optional | required | Canonical refs for specs and artifacts affected by this work item. |
| `tasks` | required; empty allowed | optional | required | Task IDs belonging to this work item. |

Rules:

- `date` uses strict `YYYY-MM-DD` format.
- Update `date` when the work-item scope or goal changes meaningfully.
- Do not update `date` for editorial corrections or task additions.
- Change `source_requirement` only to correct the originating Requirement relation.
- A `source_requirement` correction must preserve reciprocal Requirement linkage.
- Child Task `source_requirement` values must match the corrected Work Item value after a correction.
- `impact_refs` and `tasks` normalize empty values to empty lists.
- `impact_refs` and `tasks` do not accept empty list items.
- `id` in the persisted bullet metadata must match the public ID in H1 and the file name.
- Unlike ADR, `id` appears explicitly in work-item bullet metadata; it is generated by MCP on create, not supplied by the author as a metadata field.
- `impact_refs` carries machine-readable canonical refs; `## Impact Scope` carries the human-readable impact descriptions. Both represent the same scope; `## Impact Scope` is the authoritative prose form when detail is needed.

The parsing grammar is defined by `spec:drmcp.design_records_mcp.schema.metadata_grammar`.

### Status lifecycle

| status | meaning |
|---|---|
| `not_started` | Work has not yet begun. |
| `in_progress` | Work is actively under way. |
| `blocked` | Progress is stopped pending a dependency or external decision. |
| `done` | The requirement has been resolved; all required evidence and reflection are complete. |

Rules:

- When `status` is `done`, `## Goal`, `## Boundary`, and `## Evidence` must be non-empty.
- `TBD` is placeholder content, not substantive content. `TBD` must not remain in `## Goal`, `## Boundary`, or `## Evidence` when `status` is `done`.
- A work item is not `done` simply because all its tasks are done. Evidence must be recorded and the requirement must be reflected before marking `done`.
- `blocked` records an external stop; the reason belongs in `## Evidence` or a linked investigation.

### Kind-specific authoring rules

Cross-artifact selection follows `spec:product.concepts.authoring_standards.artifact_boundary`.

Work-item-specific rules:

- Every work item has exactly one source requirement in `source_requirement`.
- Record the resolution goal, not the requirement restatement, in `## Goal`.
- `## Task flow` shows execution order and dependencies — it is a view, not the canonical task status source.
- Do not copy individual task completion state into the work-item body. Individual task status is owned by each task artifact.
- Do not reproduce design rationale in the work item — use an ADR.
- Do not reproduce current specification text in the work item — use a spec.
- Put research, options, and uncertainty into an investigation, not the work item.
- `tasks` lists task IDs belonging to this work item; it does not replace task-level status tracking.

Persisted workflow relation invariants:

- The source Requirement lists this Work Item in its `work_items` field.
- Every Task listed in `tasks` references this Work Item in its `work_item` field.
- Every child Task shares the same `source_requirement` as this Work Item.

These are PRODUCT-level semantic invariants. Whether authors or DRMCP perform reciprocal updates is owned by DRMCP contracts.

Canonical ownership remains defined by `spec:product.concepts.project_artifact_model.artifact_responsibility_matrix`.

### Canonical reference policy

| Rule | Level |
|---|---|
| Reference design records by public ID. | MUST |
| Reference specs by active `spec:` semantic ref. | MUST |
| Use physical paths only as supplementary location notes. | MUST |
| Use the requirement public ID in `source_requirement`. | MUST |
| Use task public IDs in `tasks`. | MUST |

## Authoring interface requirements

### Create

The author supplies:

- app namespace;
- domain namespace;
- title;
- exact ID or `new` placeholder;
- all create-required metadata fields except `id`;
- work-item body sections.

The author does not supply:

- `id` as a metadata field;
- the resolved sequence when using `new`;
- a generated H1;
- a generated file path.

The body begins with `## Goal`. The body excludes H1 and bullet metadata. Include all canonical sections; use `TBD` for sections not yet written.

### Update

A partial update supplies only changed metadata fields or body sections.

Rules:

- Omitted metadata fields remain unchanged.
- Update `date` only when the work-item scope or goal changes meaningfully.
- Named section updates use the canonical English H2 headings.
- `id` is not a metadata update target.
- Change `source_requirement` only to correct the originating Requirement relation; see Metadata schema rules.

Concrete tool contracts belong to DRMCP specs.
