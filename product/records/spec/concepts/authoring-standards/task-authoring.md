# Reference: Task authoring

- **id**: `spec:product.concepts.authoring_standards.task_authoring`
- **status**: draft
- **date**: 2026-06-23
- **parent**: `spec:product.concepts.authoring_standards`

## What this is

Authoring rules for Task artifacts.

This guide defines task IDs, paths, file shape, metadata, lifecycle, references, and author-facing inputs.

## Non-goals

- Current DRMCP operating status.
- Concrete DRMCP request, response, or diagnostic schemas.
- Requirement or work-item authoring rules.
- Cross-artifact ownership beyond task-specific writing rules.

## Rules

### ID grammar

| Rule | Level |
|---|---|
| New task IDs use `<APP>-TASK-<DOMAIN>-<WORK-SEQUENCE>-<TASK-SEQUENCE>`. | MUST |
| `<WORK-SEQUENCE>` is the three-digit sequence of the parent Work Item. | MUST |
| `<TASK-SEQUENCE>` is a two-digit, zero-padded sequence scoped to the parent Work Item. | MUST |
| Authors may use `<APP>-TASK-<DOMAIN>-<WORK-SEQUENCE>-new` when requesting automatic sequence allocation. | MAY |
| Existing task IDs remain unchanged unless a separate migration decision requires changes. | MUST |

The canonical grammar source is `spec:product.concepts.namespace_model.artifact_id_grammar`.

### File path layout

| Rule | Level |
|---|---|
| New tasks use `<app>/records/tasks/<domain>/<APP>-TASK-<DOMAIN>-<WORK-SEQUENCE>-<TASK-SEQUENCE>-<slug>.md`. | MUST |
| The file name prefix matches the public ID through the task-sequence segment. | MUST |
| Physical paths are repository locations, not canonical references. | MUST |

The discovery pattern is defined by `spec:product.concepts.repository_layout.record_discovery_paths`.

### File shape

| Rule | Level |
|---|---|
| Use exactly one ATX H1 outside fenced code blocks. | MUST |
| Use `# <PUBLIC-ID>: <Title>` for H1. | MUST |
| Place the bullet metadata block immediately after H1. | MUST |
| Start body content at the first H2 after metadata. | MUST |

Body section schema:

| section | heading presence | substantive content | content |
|---|---|---|---|
| `## Goal` | always | required when `done` | What this task accomplishes on its own. |
| `## Work` | always | required when `done` | The concrete steps to be performed. |
| `## Done condition` | always | required when `done` | The conditions under which `status` may be set to `done`. |
| `## Verification` | always | required when `done` | How completion is confirmed. |
| `## Evidence` | always | required when `done` | Execution results and verification outcomes. Reference an ADR when the task produces a design decision. |

All canonical task headings use English.

All canonical sections must be present when creating the record, to preserve a stable document shape. Sections not yet written may contain `TBD`.

### Metadata schema

Task metadata uses H1-adjacent bullet fields.

| field | create input | partial update | persisted task | meaning |
|---|---|---|---|---|
| `id` | generated | not updated | required | The public task ID. Generated by MCP from the top-level exact ID or server-resolved `new` ID. Must match H1. Do not supply as a metadata field in a create request. |
| `status` | required | optional | required | Current task lifecycle state. |
| `date` | required | optional | required | Date the task was opened or last received a substantive scope change. |
| `work_item` | supplied as parent Work Item ID; generated into metadata | optional; correction only | required | The parent Work Item ID. Supplied by the author at the top level, not as a metadata field. MCP generates the persisted `work_item` value from it. |
| `source_requirement` | required | optional; correction only | required | The Requirement ID this task contributes to resolving. |
| `estimate` | required | optional | required | Rough effort estimate for this task. |
| `depends_on` | required; empty allowed | optional | required | Task IDs that must complete before this task can start. |
| `outputs` | required; empty allowed | optional | required | Artifacts produced or modified by this task. |

Rules:

- `date` uses strict `YYYY-MM-DD` format.
- Update `date` when the task scope or done condition changes meaningfully.
- Do not update `date` for editorial corrections or evidence additions.
- Change `work_item` only to correct the parent Work Item relation. The corrected parent must share the same app namespace, domain, and work sequence as the Task ID. Moving a task to a Work Item with a different work sequence is not a correction; create a new Task or perform an explicit migration instead. A correction must align both the old and new parent Work Item `tasks` fields and ensure the task `source_requirement` matches the corrected Work Item's `source_requirement`.
- Change `source_requirement` only to correct the originating Requirement relation. The corrected value must match the parent Work Item's `source_requirement`.
- `depends_on` and `outputs` normalize empty values to empty lists.
- `depends_on` and `outputs` do not accept empty list items.
- `id` in the persisted bullet metadata must match the public ID in H1 and the file name.
- Unlike ADR, `id` appears explicitly in task bullet metadata; it is generated by MCP on create, not supplied by the author as a metadata field.

The parsing grammar is defined by `spec:drmcp.design_records_mcp.schema.metadata_grammar`.

### Status lifecycle

| status | meaning |
|---|---|
| `not_started` | Work has not yet begun. |
| `in_progress` | Work is actively under way. |
| `blocked` | Progress is stopped pending a dependency or external decision. |
| `done` | The done condition is satisfied and evidence is recorded. |

Rules:

- When `status` is `done`, all five body sections (`## Goal`, `## Work`, `## Done condition`, `## Verification`, `## Evidence`) must be non-empty.
- `TBD` is placeholder content, not substantive content. `TBD` must not remain in any done-gated section when `status` is `done`.
- `blocked` records an external stop; the reason belongs in `## Evidence` or a linked investigation.

### Kind-specific authoring rules

Cross-artifact selection follows `spec:product.concepts.authoring_standards.artifact_boundary`.

Task granularity:

- A task SHOULD be completable within approximately 0.5d to 3d.
- Consider splitting a task when it clearly exceeds three days, contains multiple independent concerns (judgment, spec update, implementation, or verification), or its outputs and done condition cannot be described as a single completion judgment.

Task-specific rules:

- Record what this task accomplishes on its own in `## Goal`; do not restate the work-item goal.
- Record the concrete steps in `## Work`; these are authoring-time guidance, not a runtime execution log.
- Define observable completion conditions in `## Done condition`; do not use status values as conditions.
- Record execution results and verification outcomes in `## Evidence`. When the task produces a design decision, record it in an ADR and reference it from `## Evidence`.
- When a task creates or updates artifacts (specs, ADRs, investigations), record them in `outputs` and reference them in `## Evidence`. The task body is not the source of truth for those artifacts.
- Do not record design rationale in a task — use an ADR.
- Do not record current specification text in a task — use a spec.
- Do not record work-item goal state or task graph ownership in a task.
- The canonical task status is owned by the task artifact; do not copy task completion state into the parent work item.

Persisted workflow relation invariants:

- The parent Work Item lists this Task in its `tasks` field.
- This Task's `source_requirement` matches the parent Work Item's `source_requirement`.

These are PRODUCT-level semantic invariants. Whether authors or DRMCP perform reciprocal updates is owned by DRMCP contracts.

Canonical ownership remains defined by `spec:product.concepts.project_artifact_model.artifact_responsibility_matrix`.

### Canonical reference policy

| Rule | Level |
|---|---|
| Reference design records by public ID. | MUST |
| Reference specs by active `spec:` semantic ref. | MUST |
| Use physical paths only as supplementary location notes. | MUST |
| Use the Work Item public ID in `work_item`. | MUST |
| Use the Requirement public ID in `source_requirement`. | MUST |
| Use Task public IDs in `depends_on`. | MUST |

## Authoring interface requirements

### Create

The author supplies:

- app namespace;
- domain namespace;
- parent Work Item ID (used to derive the `<WORK-SEQUENCE>` segment);
- title;
- exact ID or `<APP>-TASK-<DOMAIN>-<WORK-SEQUENCE>-new` placeholder;
- all create-required metadata fields except `id` and `work_item`;
- task body sections.

The author does not supply:

- `id` as a metadata field;
- `work_item` as a metadata field — MCP generates it from the supplied parent Work Item ID;
- the resolved task sequence when using `new`;
- a generated H1;
- a generated file path.

The body begins with `## Goal`. The body excludes H1 and bullet metadata. Include all canonical sections; use `TBD` for sections not yet written.

### Update

A partial update supplies only changed metadata fields or body sections.

Rules:

- Omitted metadata fields remain unchanged.
- Update `date` only when the task scope or done condition changes meaningfully.
- Named section updates use the canonical English H2 headings.
- `id` is not a metadata update target.
- Change `work_item` only to correct the parent Work Item relation; see Metadata schema rules.
- Change `source_requirement` only to correct the originating Requirement relation; see Metadata schema rules.

Concrete tool contracts belong to DRMCP specs.
