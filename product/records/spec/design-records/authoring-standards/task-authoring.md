# Reference: Task authoring

- **id**: `spec:product.design_records.authoring_standards.task_authoring`
- **status**: draft
- **date**: 2026-07-01
- **parent**: `spec:product.design_records.authoring_standards`

## What this is

Authoring rules for Task artifacts.

This guide defines task IDs, paths, file shape, metadata, lifecycle, references, and author-facing inputs.

## Non-goals

- Current DRMCP operating status.
- Concrete DRMCP request, response, or diagnostic schemas.
- Requirement or work-item authoring rules.
- Cross-artifact ownership beyond task-specific writing rules.

## Rules

### ID grammar

| Rule | Level |
|---|---|
| New task IDs use `<APP>-TASK-<DOMAIN>-<WORK-SEQUENCE>-<TASK-SEQUENCE>`. | MUST |
| `<WORK-SEQUENCE>` is the three-digit sequence of the parent Work Item. | MUST |
| `<TASK-SEQUENCE>` is a two-digit, zero-padded sequence scoped to the parent Work Item. | MUST |
| Authors may use `<APP>-TASK-<DOMAIN>-<WORK-SEQUENCE>-new` when requesting automatic sequence allocation. | MAY |
| Existing task IDs remain unchanged unless a separate migration decision requires changes. | MUST |

The canonical grammar source is `spec:product.design_records.namespace_model.artifact_id_grammar`.

### File path layout

| Rule | Level |
|---|---|
| New tasks use `<app>/records/tasks/<domain>/<APP>-TASK-<DOMAIN>-<WORK-SEQUENCE>-<TASK-SEQUENCE>-<slug>.md`. | MUST |
| The file name prefix matches the public ID through the task-sequence segment. | MUST |
| Physical paths are repository locations, not canonical references. | MUST |

The discovery pattern is defined by `spec:product.design_records.repository_layout.record_discovery_paths`.

### File shape

| Rule | Level |
|---|---|
| Use exactly one ATX H1 outside fenced code blocks. | MUST |
| Use `# <PUBLIC-ID>: <Title>` for H1. | MUST |
| Place the bullet metadata block immediately after H1. | MUST |
| Start body content at the first H2 after metadata. | MUST |

Body section schema:

| section | heading presence | substantive content | content |
|---|---|---|---|
| `## Goal` | always | required when `done` | The one primary outcome owned by the Task. |
| `## Work` | always | required when `done` | Only actions needed to produce the primary outcome. |
| `## Implementation contract` | only when `task_type` is `implementation`; prohibited otherwise | required when an implementation Task is `done` | Target-level required change, acceptance criterion, and verification. |
| `## Done condition` | always | required when `done` | The one completion judgment for the primary outcome. |
| `## Verification` | always | required when `done` | Confirmation of the Done condition without new acceptance requirements. |
| `## Evidence` | always | required when `done` | Execution results, verification outcomes, and workflow references. |

All canonical Task headings use English.

Create every Task with all common sections to preserve a stable document shape.
Create `## Implementation contract` only for `task_type: implementation`.
Sections not yet written may contain `TBD` while the Task is not `done`.

### Metadata schema

Task metadata uses H1-adjacent bullet fields.

| field | create input | partial update | persisted task | meaning |
|---|---|---|---|---|
| `id` | generated | not updated | required | The public task ID. Generated by MCP from the top-level exact ID or server-resolved `new` ID. Must match H1. Do not supply as a metadata field in a create request. |
| `status` | required | optional | required | Current task lifecycle state. |
| `date` | required | optional | required | Date the task was opened or last received a substantive scope change. |
| `work_item` | supplied as parent Work Item ID; generated into metadata | optional; correction only | required | The parent Work Item ID. Supplied by the author at the top level, not as a metadata field. MCP generates the persisted `work_item` value from it. Task provenance is reached through this relation. |
| `task_type` | required | optional | required | Exactly one primary Task type from the closed PRODUCT-owned value set. |
| `estimate` | required | optional | required | Rough effort estimate for this task. |
| `depends_on` | required; empty allowed | optional | required | Task IDs that must complete before this task can start. |
| `outputs` | required; empty allowed | optional | required | Artifacts produced or modified by this task. |

Rules:

- `date` uses strict `YYYY-MM-DD` format.
- `task_type` is a required scalar. It permits exactly one value.
- Allowed `task_type` values are `investigation`, `decision`, `authoring`, `implementation`, `review`, `correction`, `verification`, `coordination`, and `synchronization`.
- PRODUCT owns `task_type` semantics and the closed value set.
- DRMCP owns downstream parsing, validation, diagnostics, indexing, and tool projections.
- Update `date` when the task scope or done condition changes meaningfully.
- Do not update `date` for editorial corrections or evidence additions.
- Change `work_item` only to correct the parent Work Item relation. The corrected parent must share the same app namespace, domain, and work sequence as the Task ID. Moving a task to a Work Item with a different work sequence is not a correction; create a new Task or perform an explicit migration instead. A correction must align both the old and new parent Work Item `tasks` fields.
- A Task persists no source field. Do not add `source_requirement` or `source_refs`.
- Task provenance is reached through the owning `work_item` relation.
- `depends_on` and `outputs` normalize empty values to empty lists.
- `depends_on` and `outputs` do not accept empty list items.
- `id` in the persisted bullet metadata must match the public ID in H1 and the file name.
- Unlike ADR, `id` appears explicitly in task bullet metadata; it is generated by MCP on create, not supplied by the author as a metadata field.

The parsing grammar is defined by `spec:drmcp.design_records_mcp.schema.metadata_grammar`.

### Status lifecycle

| status | meaning |
|---|---|
| `not_started` | Work has not yet begun. |
| `in_progress` | Work is actively under way. |
| `blocked` | Progress is stopped pending a dependency or external decision. |
| `done` | The done condition is satisfied and evidence is recorded. |

Rules:

- When `status` is `done`, every section required for the declared `task_type` must be substantive.
- `TBD` is placeholder content, not substantive content.
- `TBD` must not remain in any done-gated section when `status` is `done`.
- A done implementation Task must contain substantive values in every `## Implementation contract` cell.
- `blocked` records an external stop; the reason belongs in `## Evidence` or a linked investigation.

### Kind-specific authoring rules

Cross-artifact selection follows `spec:product.design_records.authoring_standards.artifact_boundary`.

#### Task type contract

| task type | primary outcome | completion judgment | prohibited overlaps | type-specific notes |
|---|---|---|---|---|
| `investigation` | One Investigation record for one bounded research question. | The Investigation satisfies its own completion requirements and the Task Done condition. | Decision adoption, canonical authoring, implementation, independent review, correction, or synchronization. | Research, evidence, uncertainty, and options remain in the Investigation. |
| `decision` | One bounded decision ledger. | Every owned item is `decided`, `deferred`, or validly `blocked`, and the Task Done condition is satisfied. | Investigation authoring, canonical ADR or Specification authoring, implementation, independent review, correction, or final synchronization. | The ledger may retain workflow Evidence defined below. |
| `authoring` | One bounded artifact set from already decided inputs. | The artifacts satisfy their authoring requirements and the Task Done condition. | Unresolved decision work, implementation, independent review, finding correction, or lifecycle synchronization. | Investigation-record authoring remains `investigation`. Finding-driven changes remain `correction`. |
| `implementation` | One bounded implementation outcome. | The Implementation contract, Task Done condition, and declared verification pass. | Unresolved design decisions, canonical design authoring, independent review, finding correction, coordination, or synchronization. | `## Implementation contract` is mandatory. |
| `review` | One bounded independent verdict and finding set. | The result is `PASS` or `NEEDS REVISION`, with complete finding Evidence and the Task Done condition satisfied. | Authoring, implementation, correction, self-closure of repaired findings, or lifecycle synchronization. | The reviewer must be independent of the reviewed authoring, implementation, or correction work. |
| `correction` | One bounded named finding set repaired. | The named repairs, Task Done condition, and direct verification pass. | Independent finding closure, unrelated improvement, new decision adoption, or lifecycle synchronization. | Finding closure belongs to a later independent `review` Task. |
| `verification` | One bounded objective acceptance gate. | Every predefined check is executed, expected and actual results are recorded, and the result is `PASS`, `FAIL`, or validly `BLOCKED`. | Artifact modification, undefined semantic judgment, repair, independent review verdict, or lifecycle synchronization. | Multiple checks may share one Task only under one acceptance gate. |
| `coordination` | One parent Work Item overview of child Work Items and responsibility boundaries. | Required child Work Items exist with distinguishable responsibilities and the Task Done condition is satisfied. | Child-owned investigation, decision, authoring, implementation, review, correction, or verification deliverables. | Child Work Items may exist before their internal Task composition is known. |
| `synchronization` | One bounded propagation of an accepted result. | All specified lifecycle, Evidence, completion-result, and relation state expresses the same accepted result. | New design judgment, decomposition, substantive deliverables, implementation, review, or correction. | Only mechanically derivable state changes are allowed. |

#### Single responsibility

Every Task must own one primary outcome and one completion judgment matching `task_type`.

Split the Task when any of these differs:

- primary outcome;
- completion judgment;
- acceptance or verification boundary;
- owner;
- release decision;
- Task type.

The approximate `0.5d` to `3d` effort range is advisory.
Effort and changed-file count are not responsibility tests.

Multiple files may remain together when every change serves one outcome and one completion judgment.
The files must also share one acceptance or verification boundary.
No file group may require a separate owner, release decision, or unresolved design decision.

#### Common section alignment

| section | required role |
|---|---|
| `## Goal` | Declare the one `task_type`-aligned primary outcome. |
| `## Work` | Include only actions needed to produce that outcome. |
| `## Done condition` | Define one completion judgment for that outcome. |
| `## Verification` | Confirm the Done condition without adding acceptance requirements. |

A supporting action associated with another Task type may remain in the Task only when it owns no separate deliverable.
The supporting action must also own no separate completion judgment.

#### Implementation contract

Only `task_type: implementation` uses `## Implementation contract`.
All other Task types prohibit the section.

Place the section in this order:

```text
## Work
## Implementation contract
## Done condition
```

Use this table shape:

| target | required change | acceptance criterion | verification |
|---|---|---|---|
| `<target>` | `<required change>` | `<acceptance criterion>` | `<verification>` |

Every cell must be substantive before the Task becomes `done`.
`TBD` is allowed only before completion.
`## Done condition` and `## Verification` must not add acceptance requirements absent from the Implementation contract.

#### Adjacent responsibility boundaries

| boundary | rule |
|---|---|
| `review` versus `verification` | Review owns semantic soundness and findings. Verification owns predefined objective criteria. Commands may support a review without creating a verification Task. |
| `correction` versus finding closure | Correction repairs a formally recorded finding. A later independent review decides `CLOSED` or `OPEN`. The correction Task must not close its own finding. |
| `coordination` versus `synchronization` | Coordination changes graph, owner, dependency, blocker, release order, or next-step structure. Synchronization only propagates accepted state. |
| implementation detail versus contract decision | Implementation may choose observable-equivalent local details. Contract, external behavior, acceptance, validation, diagnostics, persistence, fallback, or Specification changes return to `decision`. |
| `decision` versus `authoring` | Decision fixes the selected outcome and canonical target. Authoring writes those fixed inputs into canonical artifacts. |

Create a separate `verification` Task when the acceptance gate needs independent ownership, aggregation, reuse, release gating, failure routing, or post-completion evaluation.
A minor issue fixed before a formal finding exists may remain in the original Task.

Synchronization must stop when a new Task, dependency, owner, release judgment, or propagation choice is required.
Route graph changes to `coordination` and unresolved choices to `decision`.

Implementation may choose private names, helper decomposition, internal control flow, equivalent library APIs, local data structures, and test setup.
These choices must remain observable-equivalent under the accepted contract.

Authoring must stop when decided inputs allow several materially different interpretations.
The unresolved choice returns to a `decision` Task.

#### Decision workflow Evidence

A `decision` Task may retain temporary and historical workflow Evidence:

- selected option;
- rejected-option IDs;
- a concise one-to-three-sentence reason;
- canonical target;
- ADR-routing state;
- cursor and workflow state.

The Task does not own canonical durable rationale.
When an ADR is required, the ADR owns detailed rationale, alternatives, consequences, and supersession history.
The Task retains workflow history and references the canonical ADR after authoring.
A decision that does not require an ADR synchronizes directly into the relevant Specification.

#### General Task rules

- Record the Task's own primary outcome in `## Goal`; do not restate the Work Item goal.
- Record only outcome-producing actions in `## Work`; do not use it as an execution log.
- Define observable completion conditions in `## Done condition`; do not use status values as conditions.
- Record execution results and verification outcomes in `## Evidence`.
- Record created or updated artifacts in `outputs` and reference them in `## Evidence`.
- Do not record current Specification text in a Task.
- Do not record Work Item goal state or Task graph ownership in a Task.
- The canonical Task status is owned by the Task artifact.

Persisted workflow relation invariants:

- The parent Work Item lists this Task in its `tasks` field.
- Task `work_item` and Work Item `tasks` remain the explicit ownership relation.
- Task provenance is inherited only through `work_item`; the Task does not repeat Work Item `source_refs`.

Migration rules:

- Remove legacy Task `source_requirement` without replacement.
- Do not create Task `source_refs`.
- Preserve `work_item`, `depends_on`, `task_type`, and unrelated metadata and body content.
- Perform the removal in one record update.

These are PRODUCT-level semantic rules. Concrete writer and migration mechanics belong to DRMCP contracts.

Canonical ownership remains defined by `spec:product.design_records.artifact_model.artifact_responsibility_matrix`.

## Authoring interface requirements

### Create

The author supplies:

- app namespace;
- domain namespace;
- parent Work Item ID (used to derive the `<WORK-SEQUENCE>` segment);
- title;
- exact ID or `<APP>-TASK-<DOMAIN>-<WORK-SEQUENCE>-new` placeholder;
- all create-required metadata fields except `id` and `work_item`, including `task_type`; no Task source field is accepted;
- Task body sections required for the declared `task_type`.

The author does not supply:

- `id` as a metadata field;
- `work_item` as a metadata field — MCP generates it from the supplied parent Work Item ID;
- the resolved task sequence when using `new`;
- a generated H1;
- a generated file path.

The body begins with `## Goal` and excludes H1 and bullet metadata.
Include all common canonical sections.
Include `## Implementation contract` only for `task_type: implementation`.
Use `TBD` only before completion.

### Update

A partial update supplies only changed metadata fields or body sections.

Rules:

- Omitted metadata fields remain unchanged.
- Update `date` only when the task scope or done condition changes meaningfully.
- Named section updates use the canonical English H2 headings.
- `id` is not a metadata update target.
- `task_type` is an allowed metadata update target.
- A `task_type` update must realign Goal, Work, Done condition, Verification, and conditional section presence.
- Change `work_item` only to correct the parent Work Item relation; see Metadata schema rules.
- Task updates must not add `source_requirement` or `source_refs`.

Concrete tool contracts belong to DRMCP specs.
