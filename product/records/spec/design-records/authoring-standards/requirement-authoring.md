# Reference: Requirement authoring

- **id**: `spec:product.design_records.authoring_standards.requirement_authoring`
- **status**: draft
- **date**: 2026-07-01
- **parent**: `spec:product.design_records.authoring_standards`

## What this is

Authoring rules for Requirement artifacts.

This guide defines requirement IDs, paths, file shape, metadata, lifecycle, references, and author-facing inputs.

## Non-goals

- Current DRMCP operating status.
- Concrete DRMCP request, response, or diagnostic schemas.
- Design decisions that resolve the requirement.
- Work item or task authoring rules.
- Cross-artifact ownership beyond requirement-specific writing rules.

## Rules

### ID grammar

| Rule | Level |
|---|---|
| New requirement IDs use `<APP>-REQ-<DOMAIN>-<NNN>`. | MUST |
| `<NNN>` is a three-digit, zero-padded sequence scoped by app namespace, artifact kind, and domain namespace. | MUST |
| Authors may use `<APP>-REQ-<DOMAIN>-new` when requesting automatic sequence allocation. | MAY |
| Existing requirement IDs remain unchanged unless a separate migration decision requires changes. | MUST |

The canonical grammar source is `spec:product.design_records.namespace_model.artifact_id_grammar`.

### File path layout

| Rule | Level |
|---|---|
| New requirements use `<app>/records/requirements/<domain>/<APP>-REQ-<DOMAIN>-<NNN>-<slug>.md`. | MUST |
| The file name prefix matches the public ID through the sequence segment. | MUST |
| Physical paths are repository locations, not canonical references. | MUST |

The discovery pattern is defined by `spec:product.design_records.repository_layout.record_discovery_paths`.

### File shape

| Rule | Level |
|---|---|
| Use exactly one ATX H1 outside fenced code blocks. | MUST |
| Use `# <PUBLIC-ID>: <Title>` for H1. | MUST |
| Place the bullet metadata block immediately after H1. | MUST |
| Start body content at the first H2 after metadata. | MUST |

Body section schema:

| section | required | content |
|---|---|---|
| `## Requirement` | yes | The stable need, gap, or requested outcome. |
| `## Evidence` | yes | Supporting observations, records, or measurements. |
| `## Required Outcome` | required when `accepted` | Observable conditions that satisfy the requirement. |
| `## Explicitly Excluded Scope` | no | Items explicitly not in scope for this requirement. |
| `## Boundary` | no | What this requirement owns and does not own. |

All canonical requirement headings use English.

### Metadata schema

Requirement metadata uses H1-adjacent bullet fields.

| field | create input | partial update | persisted requirement | meaning |
|---|---|---|---|---|
| `id` | generated | not updated | required | The public requirement ID. Generated by MCP from the top-level exact ID or server-resolved `new` ID. Must match H1. Do not supply as a metadata field in a create request. |
| `status` | required | optional | required | Current requirement lifecycle state. |
| `date` | required | optional | required | Date the requirement was captured or last received a substantive scope change. |
| `source_refs` | required; empty allowed | optional | required | Canonical artifact IDs or active semantic refs that motivated this requirement. |

Rules:

- `date` uses strict `YYYY-MM-DD` format.
- Update `date` when the requirement scope, evidence base, or required outcome changes meaningfully.
- Do not update `date` for editorial corrections.
- `source_refs` normalizes an empty value to an empty list.
- `source_refs` does not accept empty list items.
- `id` in the persisted bullet metadata must match the public ID in H1 and the file name.
- Unlike ADR, `id` appears explicitly in requirement bullet metadata; it is generated by MCP on create, not supplied by the author as a metadata field.
- Raw observations belong in `## Evidence`; existing artifacts that record the observation should be cited in `source_refs`.

The parsing grammar is defined by `spec:drmcp.design_records_mcp.schema.metadata_grammar`.

### Status lifecycle

| status | meaning |
|---|---|
| `captured` | Requirement identified and recorded. |
| `decision_needed` | Adoption or design decision required before proceeding. |
| `accepted` | Requirement is adopted. Direct resolution links are derived from Work Item provenance. |
| `deferred` | Recognized but not currently pursued. |
| `rejected` | Not adopted. |

Rules:

- When `status` is `accepted`, `## Requirement` and `## Required Outcome` must be non-empty.
- `accepted` does not mean the requirement has been fully implemented or that associated work items are closed.
- Resolution progress and implementation steps belong in work items and tasks.

### Kind-specific authoring rules

Cross-artifact selection follows `spec:product.design_records.authoring_standards.artifact_boundary`.

Requirement-specific rules:

- Record the stable need, gap, or requested outcome.
- Record evidence that supports or motivates the requirement.
- Define the required outcome when the requirement is accepted.
- Do not record design decisions in a requirement — use an ADR.
- Do not record investigation logs, comparisons, or exploration in a requirement — use an investigation.
- Do not record current specifications or contracts in a requirement — use a spec.
- Do not record implementation progress, concrete steps, or completion state — use a work item or task.

#### Requirement identity during design convergence

| condition | required disposition |
|---|---|
| The motivating problem and Required Outcome remain the same. The change only clarifies meaning or adjusts the same outcome boundary. | Amend the existing Requirement. |
| The motivating problem or Required Outcome changes materially. The new request can be accepted or rejected independently. | Create a new Requirement. |
| The original Requirement remains completable. An adjacent additional need appears. | Create a follow-up Requirement. |
| The Requirement remains valid. A downstream decision departed from it. | Keep the Requirement unchanged and return the conflict to a `decision` owner. |

An in-place amendment makes the same Requirement accurate.
It must not absorb a materially different request or erase an independent acceptance boundary.

Requirement-to-Work-Item reverse relation:

- Requirement records do not persist `work_items` metadata.
- The direct reverse relation contains exactly the Work Items whose `source_refs` directly contain the Requirement ID.
- The direct reverse relation is an unordered, duplicate-free set.
- Transitively related descendants are excluded from the direct reverse relation.
- Transitive traversal is a separate DRMCP capability.

Migration rule:

- Remove legacy Requirement `work_items` only after exact equality with the derived direct reverse set.
- Compare both sides as unordered, duplicate-free sets.
- A mismatch blocks migration.
- Migration must not add, delete, or repair relations to force equality.

Canonical ownership remains defined by `spec:product.design_records.artifact_model.artifact_responsibility_matrix`.

### Canonical reference policy

| Rule | Level |
|---|---|
| Reference design records by public ID. | MUST |
| Reference specs by active `spec:` semantic ref. | MUST |
| Use physical paths only as supplementary location notes. | MUST |
| Use requirement public IDs in `source_refs` when referencing a prior requirement. | MUST |
| Use canonical refs rather than physical paths for every persisted relation. | MUST |

## Authoring interface requirements

### Create

The author supplies:

- app namespace;
- domain namespace;
- title;
- exact ID or `new` placeholder;
- all create-required metadata fields except `id`;
- requirement body sections.

The author does not supply:

- `id` as a metadata field;
- the resolved sequence when using `new`;
- a generated H1;
- a generated file path.

The body begins with `## Requirement`. The body excludes H1 and bullet metadata.

### Update

A partial update supplies only changed metadata fields or body sections.

Rules:

- Omitted metadata fields remain unchanged.
- Update `date` only when the requirement scope, evidence base, or required outcome changes meaningfully.
- Named section updates use the canonical English H2 headings.
- `id` is not a metadata update target.

Concrete tool contracts belong to DRMCP specs.
