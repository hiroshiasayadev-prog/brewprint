# Bootstrap validation and fixture inventory

## Status

- Derived mechanically from the runtime working contracts listed under `validation/runtime/`.
- Introduces no new runtime language, module, reference, context, event, or native-binding decision.
- Covers bootstrap configuration rejection and bootstrap-valid declaration or execution recipes only.
- Does not define operation diagnostics, record validation findings, current-reference resolution outcomes, Go implementation tests, or a fixture-loader protocol.

## Fixture policy

The current repository contains declaration examples but no fixture discovery, dependency-bundle, native-registry stub, entry-route, parser-oracle, or expected-error file format. Therefore:

- only self-contained type-declaration fixtures whose expected result is independent of a loader protocol are added now;
- each added invalid file has one intended bootstrap violation;
- function, invocation, control-flow, context, event, module, and reference cases remain inventory-only until a fixture harness can supply supporting declarations and runtime registries without creating unrelated failures;
- cases whose semantic expectation depends on an unresolved decision are marked `blocked by open decision` rather than being fixture-authored;
- existing declaration examples are migrated only as needed to satisfy the required declaration-file responsibility header without changing their intended semantic example or fixture violation.

Fixture status values:

| status | meaning |
|---|---|
| `created` | A self-contained fixture was added under `examples/valid/` or `examples/invalid/`. |
| `existing example` | An existing example demonstrates the valid declaration shape but is not yet an executable assertion fixture. |
| `inventory only` | Expected bootstrap result is fixed, but a fixture requires an undefined harness capability. |
| `blocked by open decision` | The expected result or exact fixture shape is not unique under the current contracts. |
| `document-only invariant` | The rule concerns native registration or runtime object conformance that cannot be represented by current YAML alone. |

## Blocked cases

The following expected results are not unique enough for executable fixtures under the current working contracts:

| inventory IDs | blocker |
|---|---|
| `RUNTIME-BOOT-EVENT-006` | `max_restarts` has a required finite bound, but the accepted integer domain and whether zero is valid are not stated. |
| `RUNTIME-BOOT-MODULE-005` | Cross-structure lexical discriminator equality is not specified as a catalog conflict. Same-structure duplicates are already covered. |
| `RUNTIME-BOOT-MODULE-007`, `RUNTIME-BOOT-MODULE-016` | The final required artifact capability-slot inventory remains open. |
| `RUNTIME-BOOT-MODULE-013`, `RUNTIME-BOOT-REF-005`, `RUNTIME-BOOT-REF-011` | Sequential component declaration syntax and exact native binding/conformance mechanics are owned by parallel sessions. |
| Native binding runtime fixture rows | Generated caller and binder shape is fixed, but no executable native-registry, Go-compiler, or activation-fingerprint harness is defined here. |

## Explicitly excluded

- Current-reference resolution result types and unresolved/conflicted fixtures.
- Sequential component declaration syntax.
- Exact low-level `native.Call`, `native.Binding`, descriptor, and binding-aggregation implementation interfaces beyond the generated caller and `Bind<FunctionName>` contract.
- Operation diagnostic codes or response placement, except where the runtime docs distinguish bootstrap failure from operation projection.
- Record validation findings, advisory classification, and artifact source-conformance fixtures.
- Go implementation tests.
- Semantic redesign of existing `examples/artifact/` declarations beyond the required declaration-file header migration.
